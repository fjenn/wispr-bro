## How this run was done

- **Real WebKit, not Playwright.** Every screen below is the test app's own window (WKWebView, macOS 26.6.2) captured with `screencapture -l <window id>` at 2x. A debug test hook, `WISPRBRO_HUB_ROUTE=<hash>` (test identities, debug builds only), opened Hub pages, Settings sections and the gallery on launch; onboarding steps were reached by resuming the profile at each step (`fork-settings.json` `onboarding.current_step`). Light and dark through Handy's `theme` setting; Arabic through `app_language`. Dialogs, lessons and the note were opened through the Accessibility API (AXPress on the test app's pid only); keys were posted to the test app's pid only (`CGEvent.postToPid`).
- **The screen was locked for the first ~65 minutes.** WebKit stops painting an occluded window, so the first captures were blank. A second test hook, `WISPRBRO_TEST_KEEP_PAINTING=1` (test identities, debug builds only), turns off the web view's occlusion detection for the Hub, the note and the bar, and the display was woken with `caffeinate -u` (no unlock, no input to the lock screen). AX into web content does not work while locked; it did after the owner unlocked (00:14).
- **Comparison page:** `/private/tmp/claude-501/-Users-armando/8a98ab5a-f81d-4d21-889f-f483971f85d4/scratchpad/macwave-6/index.html` (local only): 32 real-WebKit screens next to the Wispr Flow reference frame, each with a one-line verdict. Reference frames are linked by absolute local path; nothing from `docs/research/evidence/` was copied or committed. A Playwright WebKit pass of the design-shot specs (Playwright's WebKit 26.0 build, 190 shots) was used as a second look while the screen was locked.
- **Profiles.** Portable copies of the debug bundle in the session scratch dir: `fresh` (onboarding) and `done` (onboarding finished, 30 seeded history rows from `scripts/wb-s15a-seed.py`). Every launch: `wb_unbind_keys` (no global shortcut), `wb_clone_models` from `com.wisprbro.s20check` (read only), `WISPRBRO_DISABLE_UPDATER=1`, and `HF_ENDPOINT=http://127.0.0.1:9` (a dead loopback: the debug build's speech-model downloads could not leave the Mac even if setup had wanted one; none was attempted). One test copy at a time; quit by SIGTERM to its main pid.
- **Audio: the WAV microphone only** (`WISPRBRO_TEST_MIC_WAV`): `say -o` speech, the café WAVs of `scripts/wb-meter/make-wav.py` (default, `SPEECH_PEAK=0.15`, `SPEECH_PEAK=0.9`) and silence. Every launch log has `test microphone plays …` and no `Microphone (CoreAudio)` line. Nothing through the speakers; output volume 25 before and after.
- **Takes** were SIGUSR2 (hands-free) with the test app's own Hub or note in front; the second SIGUSR2 was sent only after checking the test app was still frontmost (else `--cancel`), so text could reach only the test app (see incident 1 for the one take before this guard).
- **Owner's app and data:** pid 92675 (`/Applications/Wispr Bro.app`) was never signalled or touched; nothing read or wrote `~/Library/Application Support/com.wisprbro.desktop`. No TextEdit, Mail, Notes, Messages, Slack or Cursor of the owner's was used; no target app was needed (takes went to the test app itself).
- **Clipboard:** empty before (0 items), restored by the app after each take (`clipboard restore … decision: restore`), empty after. System appearance (light), Reduce Motion and Increase Contrast were not changed (the `com.apple.universalaccess` domain is protected; see "Not run").

### Incidents

1. **One take pasted into the lock screen (product bug, fixed).** The first bar take ran while the screen was locked (W4.1 sizes, 23:24). At delivery the focused app was `loginwindow`, whose password field reads as a plain window (`container_role`), so the fail-open rule sent ⌘V there: `insert: take 1 (Take) unverified via CommandV into com.apple.loginwindow`. The text was the café WAV sentence ("Hi, I'm testing my microphone in a busy café…"), no Return was posted, the clipboard was restored after 1.5 s. The owner may have found that text in the password field when they came back. Fix `dfbc92d8`: while the session is locked or `loginwindow` has focus, a take goes to the hidden card (never pasted); unit test `the_lock_screen_gets_the_hidden_card`. No take ran while locked after that.
2. **Driver: background waiters that matched themselves** (`until ! pgrep -f "tools/cap.sh"` in their own command line) never ended and one `pkill -f pw-chrome.config` from an earlier wait stopped a later Playwright run; all were stopped and the runs repeated. No product effect.
3. **Mouse.** One `move` of the pointer (to scroll the gallery) and the test windows taking focus on launch happened while the owner was at the Mac (after 00:14). No click or key went to any window but the test app's.
