## How this run was done

- Worktree `~/Projects/wispr-bro-mac3`, `bun install`, the pinned `llama-server` sidecar copied from the main checkout. One debug build and one release build (`--bundles app,dmg`) with test identities and `createUpdaterArtifacts` off; sccache shared.
- **Profiles.** One base profile: a portable copy of the debug bundle started once with `spoken_languages = ["en"]` and every shortcut unbound (`wb_unbind_keys`), which fetched its models from Hugging Face itself (starter Parakeet TDT-CTC 110M, then Parakeet unified-en 0.6B and Muesli 2B; ~1.6 GB, the only download of the run: no test identity on this Mac had these models and `~/wb-bench` was not used). The starter was cloned aside before the policy deleted it (S-32 needs both). Then onboarding completed and update checks off; every other copy and the release profile were cloned from it (`cp -c`, `wb_clone_models`), so no further download. Only one test app ran at a time (one bundle id).
- **The owner's Wispr Bro (pid 1364) kept running** and was never signalled. Every test profile started with its shortcuts unbound; takes ran by SIGUSR2 or `--toggle-transcription`.
- **Audio: WAV microphone only** (`WISPRBRO_TEST_MIC_WAV`, `wb_mic_load`/`wb_mic_play`, `say -o` files). Nothing was played through the speakers; `WB_ALLOW_SPEAKERS` stayed unset; output volume 100 before and after.
- **Only windows this run opened got keys or text.** TextEdit ran as instances of our own (`wb_textedit_open`); every take, key and AX write checked that instance's pid first. The owner's TextEdit (pid 692) has the same bundle id, so `soak.py` was changed to activate, read and clear by pid and to cancel a take whose target lost the front before the stop (see driver fixes). No Chrome or Cursor instance was started (their launch contacts Google/Cursor servers, outside "the app's own network").
- **Clipboard.** Snapshotted at the start (`clip save`: empty, 0 types) and compared after every touching step; restored at the end.
- GUI steps that hold `~/wb-bench/gui.lock` used it; the translation agent worked in parallel (load averages quoted where they matter).
- Evidence (logs, screenshots of our own windows, AX tables, soak JSONL) stays local in the session scratch dir `m3/ev/` (never committed).

## Product failures and findings (for a fix agent)

1. **S-28.1d-f still fails, for a new reason: a take unhides the hidden app and shows its Hub.** The wave 2 fix works: in a reproduction without a take (`m3/s28_repro.sh notake`, same builds and feed) the app hidden by System Events stayed hidden (`visible=false`, no window), the scheduler logged `hub view HubView { app_hidden: false, …, main_visible: false, main_on_screen: Some(false) } → hidden true`, then `update: relaunching (hidden)` and `relaunched after an update (hidden)`, no window afterwards. With the hands-free take of S-28.1 (`s28_repro.sh take`, debug log level): `visible=false` right after the hide, **`visible=true` and the Hub window (504,146 1040×752) on screen 2 s after the SIGUSR2 that starts the take**, and it stays shown; the scheduler then correctly sees `main_visible: true, main_on_screen: Some(true) → hidden false` and relaunches shown. The same happens on an onboarded profile (c30: hidden by System Events → SIGUSR2 → `visible=true`, Hub window back), so it is not the throwaway profile's onboarding window. Symptom for a user: ⌘H the app (or close nothing but hide it), dictate, and the Hub pops back on screen at the start of every take. Likely cause: showing the bar's web view or Handy's overlay at take start orders a window of the app front, which unhides a hidden app (AppKit) — `fork/pill/panel.rs` (the web panel shown for `Bridge(…)`/`Locked`) or `src-tauri/src/overlay.rs` `show_overlay_state_on_main` (`overlay_window.show()`); an `orderFrontRegardless` on a non-activating panel without `NSApp.unhide`, or showing only when `!NSApp.isHidden`, would avoid it. Severity: medium (the Hub interrupts every take after ⌘H; S-28's relaunch then also shows it).
2. **Settings › Advanced: History Limit's number stepper has no accessible name (S-37.3).** `axtree.tsv`: `settings Advanced UNNAMED AXIncrementor value 0`, right after the named `AXTextField "History Limit"`. It is WebKit's spin button of `<Input type="number">` in Handy's `src/components/settings/HistoryLimit.tsx` (line 37); VoiceOver lands on it as an unlabelled stepper. Fix through the fork's Handy a11y layer (`settings/handyA11y.ts`, S-37a), e.g. hide the native spin buttons (`appearance: textfield`) or give the field an `inputmode="numeric"` text input, keeping Handy's file untouched. Severity: low.
3. **The first take after a fresh start waited 9 s for the LLM sidecar after its text was ready (S-38.11 first run).** Copy launched 08:51:48; the launch warm-up started the sidecar, which took 19.8 s (first Metal compile of this copy's recognizer and sidecar on a slow syspolicyd), and stopped it at 08:52:08, while a take was already transcribing; the take's cleanup then started the server again (`llama-server ready in 12698 ms`, 08:52:21) and waited for it before `cleanup: skipped light (none, already_clean …)` and the paste: transcript at 08:52:12, text in TextEdit at 08:52:21, 19 s after the stop. Two issues: the warm-up stops the server a moment before a take needs it, and the start wait is not bounded by the cleanup deadline (a later take timed out at 1,527 ms and pasted the raw text, as designed). Likely files: `fork/llm/runtime.rs` (first-launch warm-up stops the server even when a take is running) and `fork/llm/post_process.rs` / `fork/llm/supervisor.rs` (`ensure_ready` awaited without the take's deadline). A user meets it once per install or update (first take while the warm-up runs). Severity: medium.
4. **Two modals on the first Hub open:** What's New ("Welcome to the first Wispr Bro alpha", Got it) opens on top of the first-use chooser on a profile's first Hub open, the chooser's scene paused underneath; the notifications popup then follows once What's New closes (the S-37 driver now dismisses both). Not a check failure; worth a product look (one first-run modal at a time). Seen on the debug and the release identity.
5. **Environment, not product:** this Mac's syspolicyd took 58 s to clear the first exec of the copied `llama-server` (`--version` 58.5 s, then 0.01 s). In the base profile's first launch that made the app's three sidecar starts time out (`no /health after 60 s`, GPU twice, then the CPU fallback) and the first-launch warm-up fail. A notarized install should not see this; the 60 s limit and the CPU fallback after two GPU timeouts are worth knowing about if users report a slow first cleanup.

## Driver and test fixes made in this run

All in this branch, `bash -n`/`swiftc`/`ast.parse` clean, each used for the verdicts above:

- `scripts/wb-soak/axread.swift`: every reply carries the frontmost `pid`; new `activate <pid>`; with `WB_FRONT_PID` set, `clear`/`value` refuse unless that process is frontmost.
- `scripts/wb-soak/soak.py`: an app in the plan may carry the `pid` of an instance the run opened; it is then activated, read and cleared by pid only (the owner's TextEdit has the same bundle id; the old `open -b com.apple.TextEdit` + "clear the focused field" could have cleared one of the owner's documents), and a take whose target lost the front before the stop is cancelled (`--cancel`, outcome `skipped`) so nothing is pasted elsewhere. Each take record keeps the field's text (`value`, our own dictation only) to read a failure afterwards. This guard fired in the run (System Settings came forward at takes 63-66: 4 takes cancelled, nothing pasted).
- `scripts/wb-s32/run.sh`: default `STARTER`/`FULL` are the full catalog ids; the short ids (`parakeet-tdt_ctc-110m`) fail with "Model not found".
- `scripts/wb-s31/lesson.swift`: `open <title>` (focus a Radix menu/popover trigger such as Help or "Notifications, N unread" and post Space; AXPress opens nothing) and `item <title>` (focus a menu item and post Return); keys only while the app is frontmost.
- `scripts/wb-s37/run.sh` (first run on a Mac): waits for the Hub window after `open`, dismisses both first-run popups (What's New, then the notifications popup), opens Help/Notifications and the lessons with `open`/`item`, and posts Esc only after `front`; the onboarding case presses "Get started".
- `scripts/wb-s37/axtree.swift`: menu items are checked too (the Help and Notifications menus were invisible to it); AppKit's title-bar buttons (close, minimise, zoom, full screen), which have no title or description in any app (TextEdit's are the same), are recorded as `system`, not `UNNAMED`.
- `scripts/wb-perf/latency.sh`: `WB_PERF_RELEASE=1` builds the bench with `cargo test --release`.
- `src-tauri/src/fork/diagnostics/mod.rs`, `src-tauri/src/fork/testutil.rs` (tests only): two tests that use debug-only items are `#[cfg(debug_assertions)]`, so the lib test target compiles in release (it did not: E0425 `TRACE_ENV`, `bindings_language`).
