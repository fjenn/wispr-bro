## How this run was done

- Worktree `~/Projects/wispr-bro-mac2`, `bun install`, the pinned `llama-server` sidecar copied from the main checkout. One debug build and one release build with test identities; each slice ran in its own portable copy of the debug bundle (`Contents/MacOS/portable` holding `Handy Portable Mode`, ad hoc re-signed) under the session scratch dir. All copies share one bundle id, so only one test app ran at a time (the single-instance plugin is per identifier).
- **Profiles.** One base profile made by `scripts/wb-s07b/run.sh … fresh en` against the local Hugging Face stand-in (`hf-mirror.py`, Parakeet unified-en 0.6B and Muesli 2B), then cloned per slice: onboarding done, first-use choice made, VAD off (speaker audio), update checks off.
- **The owner's Wispr Bro (pid 1364) kept running.** It holds fn, fn+Space, fn+Ctrl, ⌃⌘V and ⌃⌘C, so every test profile had those actions unbound (a scratch helper writes `dictate`, `hands_free`, `command_mode`, `paste_last`, `copy_last` = `[]`), and every take was started and stopped with SIGUSR2 (Handy's toggle, the same record path). Nothing synthetic ever pressed fn.
- **Only windows this run opened got keys.** TextEdit ran as a second instance of our own (`open -n`, no restored windows; new `wb_textedit_open` in `scripts/wb-lib/app.sh`), and every key, click and take checked that instance's pid first; Chrome and Cursor ran with throwaway `--user-data-dir`s and were also checked by pid (the owner's Chrome and Cursor have the same bundle ids). The owner's TextEdit, Chrome, Cursor, Mail and Notes were never touched.
- **Audio.** No file-input path exists in the running app (`WB_ASR_WAV` is the headless bench only), so takes that need the live mic played one `say` WAV through the speakers at the current output volume, once per take (S-07b.9, S-24.1, S-29b, S-30, S-34, S-36). The §5.1 bench used WAV files only.
- **Clipboard.** Snapshotted before each touching step and compared after (digest); byte-identical after every step of this run. (Between the run start and the first take the clipboard changed by itself, from 69 to 10 bytes of plain text, not by a test: that later value was kept.)
- GUI steps ran under `/usr/bin/lockf -k ~/wb-bench/gui.lock`. A builder agent worked in parallel; load averages are quoted where they matter.
- Evidence (logs, screenshots, DB dumps, bench output) stays local in the session scratch dir `ev/` (never committed; several full-screen shots show the owner's desktop). Numbers and log lines needed for each verdict are quoted here.

## Product failures and findings (for a fix agent)

1. **A relaunch after a crash hangs behind macOS's "reopen windows?" alert (S-27.5 run).** After `kill -ABRT` of the running test app (≈ 16 s after launch), every relaunch with `--start-hidden` stopped after `System languages` and logged nothing more. `sample` showed the main thread in `-[NSApplication _reopenWindowsAsNecessaryIncludingRestorableState:]` → `-[NSPersistentUIRestorer promptToIgnorePersistentStateWithCrashHistory:]` → `-[NSAlert runModal]`: AppKit's "The last time you opened Wispr Bro …, it unexpectedly quit while reopening windows. Do you want to try to reopen its windows again?" (Reopen / Don't Reopen). Until someone answers it the app has no bar, no hotkeys and no crash notice; for an app that starts hidden at login the alert may be the only thing on screen. Pressing Don't Reopen (AX) let startup continue normally. Likely fix: opt out of window restoration at launch (e.g. `NSQuitAlwaysKeepsWindows` false / `ApplePersistenceIgnoreState`, or `applicationShouldSaveApplicationState`/restorable-state off in the app delegate); the fork's setup in `src-tauri/src/lib.rs` or the bundle's Info.plist (`tauri.fork.conf.json`). Severity: medium (only after a crash, but it blocks the whole app silently).
2. **S-28.1d-f: the update relaunch is "shown" although the app was hidden.** In `update-e2e.sh` the app (throwaway HOME, so its onboarding window was open) was hidden with System Events (`set visible … to false`, verified to work from this terminal), then a hands-free take ran; after the quiet window it installed B and logged `update: relaunching (shown)`, and the new process `relaunched after an update (shown)` with the Hub window on screen (and in front). `hub_hidden()` in `src-tauri/src/fork/update/scheduler.rs` (line ~493) only asks `is_visible()` of the `main` window; when the whole app is hidden (⌘H, System Events) that window can still report visible, so the relaunch shows it. Suggested fix: treat `NSApp.isHidden` (or "no window on screen") as hidden too. The install gate itself (`any_window_focused`) let the install through, so focus and visibility disagree here. Not proven which of the two AppKit states the window was in; reproduce with a hidden-by-⌘H Hub.
3. **The first bundled release launch registers a login item before onboarding (S-29a.5 run).** Fresh, non-portable release install launched from a disk image: `autostart::macos … Registered login item via SMAppService` at the first second of the first launch, before Welcome (macOS posts "Login Item Added"). It comes from `FIRST_RUN_DEFAULTS` `autostart_enabled = true` in `src-tauri/src/fork/settings.rs` (~line 1432, allowed for bundled release builds). S-29b's summary then offers "Open Wispr Bro when you log in" as the user's choice (DEC-38), and quitting during onboarding leaves the item registered. Not a failure of a queued check; needs a product decision (apply the default only when onboarding completes, or keep it). This run removed its item through Settings › System.
4. **§5.1 LLM cold start 5,447 ms** (budget 1,500/2,500 ms; one sample, debug Rust build with the release sidecar, load 7.4-7.8). Every other row passed with wide margins. Needs a second sample on a quiet machine and a look at what the cold start includes (`fork::perf_bench`, `llm_start_ms`) before calling it a product regression; S-12a/S-22 runs measured warm-ups of 1.1-1.5 s in the app (`llama-server ready in 1144 ms`, this run).
5. **S-24 step 3 expectation contradicted S-05** (test script, not product): a take started in TextEdit and stopped with the note focused goes into the note (key-up target), which is S-05's documented rule. MAC-TEST-SCRIPT corrected.
6. **Spurious WARN on every ordinary take:** `models: could not bind a queued take: fork.db: Query returned no rows`. `bind_entry` in `src-tauri/src/fork/models/queue.rs` (line ~98) uses `query_row` for a row that only exists for queued takes; it returns `Result<Option<i64>>`, so `.optional()` was intended. Harmless but noisy in every user's log.
7. **Hazard for future runs (driver):** `scripts/wb-f02/update-e2e.sh` runs the f02check app with a fresh profile, so its default hotkeys (fn, fn+Space, ⌃⌘V) were live for ~15 min while the owner's app was running; an owner fn press would also have started a take there. It also downloads ~1.6 GB of speech models from Hugging Face per fresh output folder. Seed the throwaway profile (unbound keys, a cloned model) before the next run.
