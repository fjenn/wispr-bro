## Product failures and findings (for a fix agent)

1. **S-28.1h/i (and so d-f) still fail: building the bar's per-take web view unhides a hidden app.** The wave 3 fix (`canHide` off on the bar's panels, `fork/pill/native.rs` `stay_when_app_hidden`) works for ordering panels in: a take started while the `fork-pill` web view already existed left the hidden app hidden. But the first take after the web view was destroyed (and every take after ⌘H, since the web view lives only ~10 s after a take) unhides the app within 1 s and brings the Hub back. Log at the take start: `Received SIGUSR2` → `pill: web view panel set to prevent activation (DEC-28)` → `pill: web view built in 27 ms` → `update: hub view HubView { app_hidden: false, … main_on_screen: Some(true) }`. In `fork/pill/panel.rs` (the web panel build, ~lines 340-395) `stay_when_app_hidden` runs only after tauri-nspanel's `.build()` returns, so whatever orders the new window in during the build (tao's window/WKWebView creation, or tauri-nspanel converting it to a panel) unhides the app first. Likely fixes: keep the web view built while the app is hidden (do not destroy it, or build it at launch), or when `NSApp.isHidden` build it and then re-hide (`NSApp.hide` without the Hub), or set `canHide` inside the builder before the first order-in. Severity: medium (after ⌘H, the Hub pops back at the first take, and S-28's quiet relaunch then relaunches shown).
2. **What's New can open during a take when the Hub is opened just after the take started (S-28.9 edge).** `WhatsNewGate.tsx` waits for `update.busy`, which `fork/update/scheduler.rs` `tick_once` samples only every 10 s (`Timing.tick`); a Hub built mid-take also never sees the take's `recording-state-event` "started". Observed: take started, Hub opened 2 s later → "What's new in 1.0.0-alpha.1" on screen for ~3 s, then unmounted when the next tick set `busy`, and it came back after the take. Fix: have the gate also read the take state directly (e.g. the coordinator's busy flag through a command at mount plus `recording-state-event`, as `featurePopupGate.ts` `useTakeRunning` does for the popup), or publish `busy` on take start/stop instead of on the tick. Severity: low (needs an update, then opening the Hub within seconds of starting a take).
3. **Note, not a failure:** the one-time notifications popup reads "New in this version" on a brand-new install (after Maybe later on the chooser). It is the only first-run modal after the chooser, as designed by finding 4's fix; the wording is odd for a first install.

## Driver and test fixes made in this run

All in this branch, `bash -n`/`swiftc` clean, each used for the verdicts above.

- **Debug builds write `../src/bindings.ts` relative to their working directory** at every start (Handy's specta export). Every driver that ran the app from the checkout wrote a stray `~/Projects/src/bindings.ts` next to it (it predates this run, from earlier waves; left in place), and a debug app started by LaunchServices (`open -a`, cwd `/`) panics on the read-only disk (`Failed to export typescript bindings: … Read-only file system`) before it forwards anything to the running instance. `scripts/wb-s37/run.sh`, `scripts/wb-s10/first-take.sh` and `scripts/wb-f02/update-e2e.sh` now start the app from a folder under their output dir.
- `scripts/wb-s37/run.sh`: opens the Hub with a second launch of the same executable (the single-instance plugin forwards it; retried while the first instance is not yet listening) instead of `open -a`; dismisses the first-use chooser ("Maybe later") before the popups (the wave 3 profile had answered it, a fresh profile has not: every page was "not found" in this run's first attempt); starts the app with a silent test microphone so the real one is never opened.
- `scripts/wb-s10/first-take.sh` (first run on a Mac): starts the app hidden (shown, the Hub took the front and the take pasted into the app itself); checks our TextEdit is frontmost by pid before the take and before the stop (else quits the app before the stop, nothing pasted); does the slow focus work before the model is ready and starts the take at once (a warm-up with compiled shaders takes 0.4 s, less than two `osascript` calls); waits for the delivery line `insert: take 1 (Take) ` rather than the earlier `insert: take 1 target` decision line; new check **S-10.9d**: the paste went to `com.apple.TextEdit`. Run it on a bundle copied to a new path to get the several-second warm-up an install sees.
- `scripts/wb-s31/lesson.swift`: `focus <title>` / `value <title>` (the text field first when a row and its field share the name) and `key up`, for S-37.4's ↑ by hand.
- **Not committed:** this run's S-28.9 and S-28.1 repro scripts (`s289.sh`, `repro*.sh`, `hide.sh`, `relsmoke.sh`) stay in the session scratch. Lessons from them: copies of one identity must not overlap (wait until no process of it runs before the next launch); WebKit fills its AX tree lazily (read for several seconds); `pkill -f <bundle executable>` also kills the sidecar watchdog (a fork of the app with the same command line), which left two `llama-server` processes with ppid 1 in this run (stopped by hand): quit the main pid instead.
