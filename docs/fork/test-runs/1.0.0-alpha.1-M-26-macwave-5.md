## How this run was done

- Worktree `~/Projects/wispr-bro-mac5`, `bun install`, the pinned `llama-server` sidecar copied from the main checkout (`build.sh --if-missing` accepted its stamp); sccache shared.
- **Profiles.** One base profile in a portable debug copy (`Contents/MacOS/portable` + `Data/`), seeded with every shortcut unbound (`profile.py unbind`) and the model cache cloned from `com.wisprbro.s20check` (`profile.py models`), started once (`UseOther` → Whisper large-v3 turbo on disk, hotkey trigger `None`), then onboarding marked finished in the files (Handy's `onboarding_completed`, the fork's `onboarding.status = completed`, update checks off). An "updated" profile was made from it: Hub opened once, the first-use chooser answered "Maybe later" and the notifications popup "Got it" (so `dismissed_banners` = `first-use.chooser`, `feature.inbox`), quit, then `whats_new_last_seen_version` set to `0.9.7`. Every check ran on its own `cp -c` copy, started from its own folder (no `../src/bindings.ts` outside the scratch dir).
- **Audio: the WAV microphone only** (`WISPRBRO_TEST_MIC_WAV`): silent WAVs (S-28, S-28.9, the ⌘H extra) or one `say -o` WAV of "Please send the quarterly report to the team by Friday." (smoke, S-24.1); nothing through the speakers; output volume 25 before and after. Before every take the driver checked: the pid is the process launched with the WAV and the only main process of the identity, the log of this launch has exactly one `fork ready` and `test microphone plays <wav>`, and no `opened … Microphone (CoreAudio)`. One driver incident, see below.
- **Single copy.** No launch while any process of the identity (main, watchdog fork, sidecar) still ran; apps were quit by SIGTERM to the main pid (no broad `pkill -f`); after the run no `llama-server` or test process was left.
- **The owner's Wispr Bro and TextEdit** (pids 1364 and 692) were never signalled, typed into or read. Takes into TextEdit went into an instance this run opened (`wb_textedit_open`), each only after that pid was checked frontmost; ⌘H was posted only with the test app's pid frontmost. ⌥S was not posted (the owner's app may bind it); the note was opened from the Hub instead.
- **Clipboard.** Snapshot at the start (empty, 0 items); the smoke takes set a sentinel string before each take and compared it after; restored to the empty snapshot at the end.
- **Credentials (Part B).** `macos.sh` read the Developer ID, the notary profile `wispr-bro-notary`, `~/.wispr-bro/updater.key` and its keychain password itself. No dialog and no prompt appeared at any step; nothing secret was printed, copied or committed. Nothing was published: no push, no GitHub release, no upload except the two notarization submissions `macos.sh` makes.
- Evidence (logs, screenshots of our own windows, AX dumps) stays local in the session scratch dir `m5/` (never committed).

### Driver incidents (mine, not product)

1. **Base profile launched once unseeded.** `wb_unbind_keys`/`wb_clone_models` were called after sourcing `app.sh` from an interactive shell, where `BASH_SOURCE` did not resolve the library dir; `profile.py` was not found and the base copy started with its default shortcuts and no models. In ~95 s (hidden, no window) it downloaded Parakeet v3 (739 MB, checksum ok) and began the turbo download from Hugging Face (the app's own HF use); no take ran (`history.db` 0 rows, `recordings/` empty, no `insert:` line), no key was posted by the driver. The profile was deleted and rebuilt with `profile.py` by absolute path (no download afterwards).
2. **A second launch became the app once (S-28.9 control, first attempt).** The copied profile carried the previous launch's log, so `launch()` matched a stale `test microphone plays` line and returned while the new instance (new path, slow first start) was not yet listening; the Hub-opening second launch (no WAV variable) got the single-instance socket, the WAV-microphone launch handed over to it and exited. That plain instance logged `opened MacBook Pro Microphone (CoreAudio) … microphone prepared (input unit built, not started)`: the built-in microphone's input unit was built but never started, no take was sent, nothing recorded; the process was stopped after ~25 s and the profile deleted. The driver now truncates the copied log, requires one fresh `fork ready` from the launched pid plus its own test-microphone line and `startup: ready` before any Hub open, refuses any take after a second app start or a real-microphone line, and waits up to 30 s for a second launch to exit. Every later launch passed these guards.
