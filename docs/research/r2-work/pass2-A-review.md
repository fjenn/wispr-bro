## Open questions resolved

1. **How handy-keys handles fn/Globe** (pass-1 open item 7, A-35). verified-in-code.
   - The fn key arrives as `FlagsChanged` with keycode 0x3F. The FN state comes from `MaskSecondaryFn` (`handy-keys/platform/macos/listener.rs:320-340`; `keycode.rs:276-278`).
   - The tap blocks only the **press** of a registered modifier-only hotkey (`listener.rs:331-333`; the generic modifier path is `:310-312`). The fn **release** FlagsChanged is always passed through.
   - A KeyDown with an unmapped keycode (for example the Globe key's configured system action) is passed through (`listener.rs:224-230`).
   - So whether macOS still runs the Globe action (emoji picker, input source, Apple Dictation) when the press is blocked but the release is not is still `unknown`. It needs a runtime test. The likely safe path is onboarding asking the user to set "Press 🌐 to: Do Nothing", or binding `fn+dictation` (A-202).
2. **Can the overlay panel receive mouse events?** Partly resolved.
   - The panel does not ignore mouse events. No `ignores_mouse_events` call (`overlay.rs:456-476`), and the ✕ is wired to a click handler (`RecordingOverlay.tsx:244-259`).
   - tauri-nspanel supports `accepts_mouse_moved_events`, tracking areas and `mouseEntered` / `mouseMoved` handlers (`nspanel/builder.rs:215-260`, `:629-636`; `panel.rs:27-29`).
   - Still unknown: whether the first click reaches the WKWebView, because macOS has `acceptsFirstMouse` = false (see the A-07 correction).
3. **No focused text field.** verified-in-code.
   - Handy writes the clipboard, sends Cmd+V blindly, then restores the old clipboard, or clears it if it held nothing (`clipboard.rs:74-138`).
   - The transcript then survives only in History, and on the clipboard only if `CopyToClipboard` is set (A-204).
   - No `paste-error` fires, because the injection "succeeds". So A-53 (paste failure feedback) almost never triggers in this case. The "no textbox" case needs A-51 detection; error routing alone will not catch it. inferred
4. **Does a modifier-only fn hotkey release correctly during fn+key chords?** verified-in-code. No. A keyed event never releases a key-less hotkey (`handy-keys/manager.rs:56-75`), so the fn hotkey stays pressed until fn is released. This confirms the A-22 accident risk.
5. **Can mouse buttons be recorded as hotkeys (A-28 "unknown")?** Mostly yes. inferred from code:
   - The tap reports middle and side buttons (X1/X2) always, and left/right only with a modifier held (`handy-keys/platform/macos/listener.rs:346-419`).
   - The recorder forwards `key.to_string()` and `to_handy_string()` (`shortcut/handy_keys.rs:313-323`), and keyed combos commit on key-up (`src/hooks/useShortcutCapture.ts:143-158`).
   - Whether the recorder's `KeyboardListener` uses the same event mask, and so receives mouse events, was not checked line by line. Runtime `unknown`.
6. **Is the hold threshold exposed to users?** verified-in-code. Only in Debug (`debug/HoldThreshold.tsx`); onboarding reads it (`useTryEngine.ts:46`).
7. **Is activation mode per binding?** verified-in-code. No. One global `shortcut_activation` is passed for every transcribe binding (`shortcut/handler.rs:37-46`). Wispr's model ("hold fn" plus a separate hands-free toggle binding) needs per-binding modes. This adds to A-24.
8. **Launch at login default** (pass-1 open item 8, our side). verified-in-code. On after onboarding (A-64 correction).
